# スレッド命名 (手動 + AI) — 設計書

- 日付: 2026-08-31
- ステータス: 設計中 / 実装未着手
- 対象バージョン: v0.2.0 (手動命名) / v0.3.0 (AI 命名)
- 前提設計: `docs/superpowers/specs/2026-08-29-threadswork-design.md`

## 1. 目的

スレッドカードの見出しが現状「起点メッセージの送信者名」しかなく、一覧を眺めても
どのスレッドが何の話なのか判別できない。スレッドに名前をつけられるようにする。

手でつけるのが基本。名前をつけるのが面倒な利用者のために、AI に任せられる
有料オプションを用意する。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 手動命名 | 無料。全利用者。 |
| AI 命名 | 有料。月額サブスクリプション。 |
| BYOK (利用者が自分の Gemini API キーを貼る方式) | **採らない。** 課金する理由が消えるため。 |
| ヒューリスティック自動命名 (本文冒頭の機械的な切り出し等) | **実装しない。** 下記 2.1。 |
| 名前の共有 | しない。個人メモ。他の参加者には見えない。 |

### 2.1 ヒューリスティック自動命名を実装しない理由

「起点メッセージの1文目を20文字で切る」だけで、AI 命名が狙う体験の7割は無料で
再現できてしまう。それを載せると有料機能が売れない。これは技術上の判断ではなく
値付けの判断であり、この設計書に明記して以後の判断のブレを防ぐ。

同じ理由から、**AI 命名が失敗したときもヒューリスティックへフォールバックしない。**
失敗はエラーとして表示し、再試行させる。

## 3. 既存の設計原則との衝突

前提設計 §1 は設計原則の第1項に「完全クライアントサイド完結 — バックエンドを持たない。
ネットワーク通信を一切行わない」を掲げている。AI 命名はこれを破る。

さらに、**公開済みのストア掲載文とプライバシーポリシーが、通信しないことを明示的な
売りとして書いている。**

- `docs/store/listing.md:68` 「この拡張は、外部のサーバーと一切通信しません。」
- `docs/store/privacy-policy.md` 「本拡張は、いかなる情報も収集しません。」
- ストアのデータ申告で「個人的な通信内容」「ウェブサイトのコンテンツ」を **収集しない** と申告済み

これは v0.3.0 の**リリース条件**であって、実装の後始末ではない。順序を間違えると
虚偽申告になる。

### 3.1 衝突の解き方

原則を捨てるのではなく、通信する範囲を極小に隔離して「既定では通信しない」を
真のまま維持する。

1. **既定は無効。** 利用者が設定で明示的に有効化しない限り、`fetch` は一度も呼ばれない。
2. **通信コードは service worker (`src/background.js`) にのみ置く。** content script には
   `fetch` を一切書かない。「Chatwork のページ上で動くコードは通信しない」は維持される。
   content script は `chrome.runtime.sendMessage` でリクエストするだけ。
3. **送信は利用者の明示操作の単位でのみ。** そのスレッドの「AI で名前をつける」を押した
   ときに、そのスレッドの本文だけを送る。ルーム全体やバックグラウンドでの先読みはしない。
4. **送信者名を送らない。** 話者は `A` / `B` / `C` に匿名化して送る (§6.2)。氏名は名前の
   生成品質にほぼ寄与しない一方、送信データの機微さを大きく上げる。
5. **`host_permissions` を増やさない。** service worker からの fetch は、サーバー側が
   `Access-Control-Allow-Origin: chrome-extension://<id>` を返す形にして CORS で解決する。
   host permission を足すとインストール時に警告が出て、審査も重くなる。

> **要確認 (実装前):** MV3 の service worker からの cross-origin fetch が、host permission
> なし + サーバー側 CORS ヘッダのみで通ることを実機で検証する。通らなければ
> `host_permissions` 追加に切り替える (警告文言の増加を受け入れる)。

### 3.2 v0.3.0 で必須になる書類変更

- `docs/store/privacy-policy.md` の全面改訂。「一切収集しません」を維持できない。
  「既定では送信しない。AI 命名を有効にし、かつ利用者が個別に実行したときにのみ、
  対象スレッドの本文 (送信者名を除く) を当社サーバー経由で Google の Gemini API へ送信する」
- `docs/store/listing.md:68-72` の書き換え
- ストアのデータ申告: 「個人的な通信内容」「ウェブサイトのコンテンツ」を送信ありへ変更
- 有料機能があることの明示 (ストアの「アプリ内購入」相当の記載)

## 4. データモデル

### 4.1 保存形式

`chrome.storage.local` に**ルームごとに1アイテム**でまとめる。

```
キー:   "names:{roomId}"
値:     { v: 1, items: { [rootId]: { name: string, by: "user" | "ai", at: number } } }
```

- `at` は UNIX 秒。破棄の優先順位に使う。
- ルーム単位に束ねる理由は3つ。スレッド1件1アイテムにするとアイテム数が容易に数千に
  達すること、将来 `chrome.storage.sync` (512 アイテム上限) へ移すときに設計を変えずに
  済むこと、ルーム離脱時にキー1つで捨てられること。
- メッセージ ID・ルーム ID は 19 桁前後の数値文字列。**`Number()` 化しない** (前提設計の制約)。

### 4.2 rootId が変化する問題

**これは実装上の最大の落とし穴で、素朴に作ると必ず壊れる。**

`buildThreads` の `findRoot` は「**その時点で DOM に読み込まれている中での**最上位の祖先」を
返す。利用者がタイムラインを上にスクロールして親メッセージが読み込まれると、同じ会話の
`rootId` が `B` から `A` へ変わる。名前を `rootId` にだけ紐づけると、名前をつけたスレッドが
スクロールした瞬間に無名に戻る。

**解決:** 名前の解決は「そのスレッドに属する全メッセージ ID のうち、保存済みの名前を持つ
もの」を探す形にする。複数見つかった場合は根に近い (depth の小さい) ものを採る。

```
resolveName(thread, items) -> { name, key } | null
```

さらに、解決した `key` が現在の `thread.rootId` と異なる場合、新しい `rootId` へ**付け替えて
保存し直す** (古いキーは削除)。これで再ルート化のたびに探索コストが増えることはない。

`rootIsSynthetic` (親未読み込み) のスレッドは、この付け替えが特に頻繁に起きる。

### 4.3 上限と破棄

- 1ルームあたり **200 件**。超えたら `at` の古い順に捨てる。
- `by: "ai"` と `by: "user"` を区別する理由は、破棄の優先順位ではなく、AI 生成の名前を
  利用者が手で直したときに `by: "user"` へ昇格させ、以後の一括再生成の対象から外すため。
- ルーム離脱・メッセージ削除でキーは孤児化するが、上限と LRU 破棄で十分に吸収される。
  能動的な回収処理は作らない (YAGNI)。

## 5. UI 仕様

### 5.1 表示

名前があるとき、カード見出し (`thread__name`) を名前に差し替え、送信者名はメタ行へ降ろす。
名前がないときは現状どおり送信者名を見出しにする。

```
[アイコン]  請求書フォーマットの件            3分前   >
            返信 4 件 · 三沢慎吾
```

### 5.2 編集

- カードの見出し右に鉛筆ボタン。ホバーおよびフォーカス時に出す。
- 押すと見出しがその場で `<input>` に変わる。Enter で確定、Esc で取り消し、blur で確定。
- 空文字で確定したら名前を削除して送信者名表示に戻す。
- 最大 40 文字。前後の空白を落とし、連続空白と改行は空白1つへ潰す。

### 5.3 AI 命名の導線

- **AI 命名が無効な間は、パネルに関連 UI を一切出さない。** 無効なのに押せるボタンを置くと、
  「押したら課金案内が出る」体験になり、通信しない拡張としての信頼を損なう。
  機能の存在の告知はオプションページとストア掲載文で行う。
- 有効時、カード見出しの右に「AI」ボタン。押したスレッド 1 件を命名する。
- パネルヘッダに「無名のスレッドをまとめて命名」を置く。**1 回の操作で最大 20 スレッド**まで。
  それ以上は繰り返し押させる (誤操作で大量送信させないため)。対象は「返信があり、かつ
  まだ名前が無いスレッド」に限る。
- 実行中はボタンを `disabled` にして二重送信を防ぐ。
- 残り生成回数をヘッダに小さく表示する (サーバー応答から受け取る)。

### 5.4 設定 UI

有効化とライセンスキーの入力は、拡張のオプションページ (`manifest.json` の `options_page`) で行う。
パネル内には置かない。パネルは Chatwork の画面上に出るため、ライセンスキーの入力欄を
そこに置くと、画面共有中に映る事故が起きる。

## 6. AI 命名の仕様

### 6.1 生成する名前

- 日本語の名詞句。**12〜20 文字**を目安、最大 24 文字。
- 文末の句点を付けない。「〜について」「〜の件」の多用を避ける指示を入れる。
- 生成結果が 24 文字を超えたらクライアント側で切り詰める (サーバー任せにしない)。

### 6.2 送信するデータ

1スレッドあたり:

- 起点メッセージ本文 (最大 400 文字)
- 返信のうち先頭 10 件、各最大 200 文字
- 話者は出現順に `A` / `B` / `C` … へ匿名化。**氏名・アカウント ID は送らない。**
- 添付ファイル名、URL、`[info]` 等の Chatwork タグは本文からそのまま渡す (除去しない)。
  ここを削ると話題の手がかりが落ちる。

送らないもの: 送信者名、アカウント ID、ルーム ID、メッセージ ID (対応付けは
クライアントが握るローカルな連番で行う)、Chatwork の認証情報 (そもそも扱っていない)。

### 6.3 失敗時

エラーを通知領域に出して終わり。ヒューリスティックへ落とさない (§2.1)。
再試行はボタン再押下。連続失敗時のリトライ自動化はしない。

## 7. サーバー契約

サーバーは**この拡張とは別リポジトリ・別計画**とする。ここでは拡張が依存する契約だけ固定する。

```
POST https://api.<domain>/v1/name
Content-Type: application/json

{
  "licenseKey": "string",
  "threads": [
    { "ref": "0", "messages": [ { "speaker": "A", "text": "..." } ] }
  ]
}
```

成功 (200):

```json
{ "names": { "0": "請求書フォーマットの件" }, "remaining": 183 }
```

エラー:

| ステータス | `code` | クライアントの表示 |
|---|---|---|
| 401 | `invalid_license` | ライセンスキーが正しくありません |
| 402 | `quota_exceeded` | 今月の生成回数を使い切りました |
| 429 | `rate_limited` | 混み合っています。少し待って再実行してください |
| 5xx | — | 生成に失敗しました。時間をおいて再実行してください |

- `ref` は**そのリクエスト内でのみ有効な連番**。メッセージ ID を送らないための対応キー。
- タイムアウトはクライアント側 20 秒。
- サーバーは受け取った本文を保存しない。ログにも残さない (プライバシーポリシーに明記する内容)。

## 8. 課金

- **Chrome ウェブストアの課金機能は終了しているため、自前決済が必要。** Stripe Checkout +
  ライセンスキー発行。(要再確認)
- ライセンスキーは `chrome.storage.local` に保存。検証はサーバー側のみ。クライアントに
  検証ロジックを置かない。**有料機能の実体がサーバー側の推論なので、キーの偽装は原理的に
  無意味**であり、この設計は素直に成立する。
- 価格は未決定 (§10)。

## 9. スコープ外

- ピン留め (§4 のストレージ層を再利用して別計画で作る)
- 名前のチーム共有
- 名前による検索・絞り込み
- 複数端末同期 (`chrome.storage.sync` への移行)
- 名前の自動再生成 (スレッドに返信が増えたときの追従)

## 10. 未決定事項

1. **価格。** 提案は月額 100 円。カード入力の摩擦とサポート原価は 100 円でも 500 円でも
   同一なので、300〜500 円を推す。原価 (Gemini Flash 系で 1 スレッドあたり 0.02〜0.03 円
   程度、かつ生成結果は永続キャッシュされ再生成不要) はどちらでも問題なく吸収できる。
2. 無料枠を設けるか (例: 月 20 件まで無料)。設ければ課金導線を持ったまま需要を検証できる。
3. モデルの選定 (Gemini Flash / Flash-Lite)。単価と品質の実測が必要。
4. 法人向けの請求書・インボイス対応の要否。
5. サーバーのホスティング先。
